## 三、检索策略（Retrieval）

### Q5：什么是混合检索？为什么需要混合检索？

#### 单一检索的局限

**纯向量检索（Dense Retrieval）**：
- ✅ 擅长语义匹配（"苹果手机" → "iPhone"）
- ❌ 对专有名词、精确关键词不敏感（"Python 3.12" 可能检索到 "Python 2.7"）

**纯关键词检索（Sparse Retrieval / BM25）**：
- ✅ 擅长精确匹配（"Python 3.12" 精确匹配）
- ❌ 无法理解语义（"手机" 和 "智能手机" 被视为不同词）

#### 混合检索的优势

**核心思想**：结合两者的优势，互补不足

**典型架构**：
```
用户查询
   │
   ├─→ Dense 检索（向量）→ top-k 文档
   │
   └─→ Sparse 检索（BM25）→ top-k 文档
   │
   └─→ RRF 融合 → 最终结果
```

**效果提升**：
- 召回率提升 15-25%
- 对不同类型查询都有良好表现

#### 实际案例

查询："LangGraph 的 State 怎么定义？"

- **向量检索**：找到"LangGraph 状态管理"相关文档（语义匹配）
- **BM25 检索**：找到包含"State"、"定义"关键词的文档（精确匹配）
- **融合后**：两者结合，召回更全面

---

### Q6：混合检索中 Weighted Ranker 和 RRF 的区别是什么？参数如何设置？

#### Weighted Ranker（加权融合）

**核心思想**：将不同检索器的分数按权重相加。

**公式**：最终分数 = w₁ × 向量检索分数 + w₂ × BM25 分数

**推荐参数**：权重比例 7:3（向量 70%，BM25 30%）

**工作原理**：
- Dense 检索（向量）擅长语义匹配，分数范围 [0,1]
- Sparse 检索（BM25）擅长关键词匹配，分数范围不固定
- Milvus 内部先对两路分数做归一化到 [0,1]，再按权重加权

**缺陷**：依赖分数归一化的准确性。如果某次检索只有少量结果，归一化后分数分布可能失真，导致融合不公平。

#### RRF（Reciprocal Rank Fusion，倒数排名融合）

**核心思想**：只看排名不看分数，从根本上避免分数归一化问题。

**公式**：RRF 分数 = Σ (1 / (k + 排名))

**推荐参数**：k=60（原论文通过大量实验得出的最优值）

**工作原理**：
- k=60 让排名靠前和靠后的文档分数差距约 1.2 倍
- 两路检索结果能公平融合，不会因为某一路分数高就主导结果
- 例如：文档 A 在向量排第 1、BM25 排第 3；文档 B 在向量排第 2、BM25 排第 1。RRF 会认为 B 更均衡，排在前面。

#### 对比总结

| 维度 | Weighted | RRF |
|------|----------|-----|
| 需要调参 | 需要（权重比例） | 几乎不需要（k=60 通用） |
| 对分数分布敏感 | 是 | 否（只看排名） |
| 推荐场景 | 分数已归一化、精细调优 | **通用场景，默认首选** |

**结论**：优先使用 RRF（k=60），鲁棒性更强，适合大多数 RAG 场景。

### Q7：BM25 的 k1 和 b 参数分别控制什么？

**BM25 是一种经典的关键词检索算法**，基于词频统计和文档长度归一化。

**k1（默认 1.2）**：控制词频饱和度
- k1 越大，高频词的贡献越大
- k1=0 时退化为布尔模型（只看词是否出现，不考虑出现次数）
- 典型取值范围：1.0~2.0

**b（默认 0.75）**：文档长度归一化因子
- b 越大，对长文档的惩罚越重
- b=0 完全不考虑文档长度
- b=1 完全按长度归一化
- 典型取值范围：0.5~1.0

**实际意义**：
- 短文档中的关键词出现一次就很显著
- 长文档中的关键词需要出现多次才算重要
- BM25 通过这两个参数平衡词频和文档长度的影响

### Q8：RRF 中 k 值的大小对融合结果有什么影响？

**k 值控制排名衰减的速度**：

| k 值 | rank=1 贡献 | rank=10 贡献 | 衰减比 | 特点 |
|------|------------|-------------|--------|------|
| 1 | 0.500 | 0.091 | 5.5x | 极端精英制，top-1 主导 |
| 10 | 0.091 | 0.050 | 1.8x | 较激进 |
| **60** | **0.016** | **0.014** | **1.2x** | **温和衰减，推荐值** |
| 100 | 0.010 | 0.009 | 1.1x | 几乎无差异 |

**k 太小的问题**：
- 向量检索的 top-1 完全压制 BM25 结果
- 失去混合检索的意义，变成单路检索

**k 太大的问题**：
- 所有排名的贡献几乎相同
- 等于没有排序，融合失去意义

**k=60 的优势**：
- 各排名贡献接近但仍有区分度
- 是公平融合与有效排序的最佳平衡点
- 经过 TREC 等权威数据集验证

### Q9：CrossEncoder 是什么？怎么做 Rerank？

#### Bi-Encoder vs CrossEncoder

**Bi-Encoder（双塔模型）**：
- Query 和 Document **分别**编码为向量，再算余弦相似度
- 速度快：文档向量可预计算，检索时只算 query 向量 + ANN 搜索
- 精度较低：两段文本独立编码，无法捕捉细粒度交互
- 用途：**召回阶段**（从百万文档中快速筛选 top-k）

**CrossEncoder（交叉编码器）**：
- Query 和 Document **拼接**后一起输入 Transformer，直接输出相关性分数
- 速度慢：每对 query-doc 都要过一次完整的 Transformer
- 精度高：query 和 doc 的每个 token 都能互相 attend（注意力机制）
- 用途：**精排阶段**（对 top-k 结果重新排序）

#### CrossEncoder 的工作原理

```
输入：[CLS] query tokens [SEP] document tokens [SEP]
                    ↓
          Transformer（如 BERT）
                    ↓
          [CLS] 的隐藏状态 → 线性层 → sigmoid → 相关性分数（0~1）
```

**关键优势**：Query 和 Document 的所有 token 在 Transformer 的每一层都能通过 Self-Attention 互相交互。

**举例理解**：
- "苹果发布了新手机" 中的"苹果"是公司，而非水果
- "Python 的 GIL 是什么" 与 "全局解释器锁限制了多线程并发" 的深层语义关联

Bi-Encoder 做不到这一点，因为 query 和 doc 是独立编码的，只在最后算一个余弦相似度。

#### Rerank 流程

```
用户查询
    │
    ├─ 第一阶段：Bi-Encoder 召回（快，毫秒级）
    │   └─ 从百万文档中检索 top-k（如 k=20）候选文档
    │
    └─ 第二阶段：CrossEncoder 精排（慢，但精准）
        ├─ 将 query 与每个候选文档拼接为 (query, doc) 对
        ├─ 逐对输入 CrossEncoder，得到相关性分数
        ├─ 按分数降序排列
        └─ 过滤低于阈值的文档，返回最终结果
```

#### 为什么需要 Rerank？

**Bi-Encoder 的局限**：
- 向量检索本质是"近似最近邻搜索"
- 召回的 top-k 中可能有语义相关但不精确匹配的噪声文档
- 余弦相似度只衡量向量空间中的距离，无法捕捉 query 和 doc 之间的细粒度语义交互

**CrossEncoder Rerank 的价值**：
- 将 top-k 中真正相关的文档排到前面，噪声文档排到后面或过滤掉
- 实验表明，Rerank 可以将 RAG 的答案准确率提升 **10-20%**

#### 注意事项

- **max_length=512 的限制**：超过 512 token 的文档会被截断，长文档可能丢失关键信息。改进方案：对长文档采用滑动窗口，取各窗口的最高分
- **计算成本**：CrossEncoder 的时间复杂度是 O(k)，所以第一阶段的 k 不宜过大，通常 10-30 为宜
- **阈值选择**：默认 threshold=0.8，较为严格。如果召回文档质量普遍不高，可适当降低到 0.5-0.6

### Q10：近似去重时选择 0.92 作为阈值，这个值是如何确定的？

#### 阈值选择的经验法则

- **0.90~0.95**：适合大多数 RAG 场景，能有效过滤语义重复的文档
- **0.92**：经过实验验证，在中文场景表现良好

#### 阈值过高（如 0.98）的问题

**误删非重复文档**：语义相近但不完全相同的文档可能被误判为重复

**示例**：
- 文档 A："Python 是一种编程语言"
- 文档 B："Python 是一门流行的编程语言"
- 相似度 0.95，如果阈值 0.98 则保留两者，如果阈值 0.92 则删除 B（可能误删有价值的变体表达）

#### 阈值过低（如 0.85）的问题

**保留过多重复文档**：语义高度相似的文档仍然保留，浪费 token

**示例**：
- 文档 A："RAG 是检索增强生成技术"
- 文档 B："RAG（Retrieval-Augmented Generation）是检索增强生成技术"
- 相似度 0.88，如果阈值 0.85 则保留两者，造成冗余

#### 如何通过实验确定最优阈值

**方法**：在评估数据集上测试不同阈值，选择使检索精确率最高的阈值。

**步骤**：
1. 准备评估数据集（包含查询和相关文档）
2. 对每个阈值计算去重后的检索质量
3. 计算平均精确率
4. 选择精确率最高的阈值

**典型测试范围**：[0.85, 0.90, 0.92, 0.95, 0.98]

## 一、文档切分（Chunking）

### Q1：为什么需要对文档进行切分？直接整个文档检索不行吗？

#### 核心原因

**1. Token 限制**
- LLM 有上下文窗口限制（如 8K/32K tokens）
- 长文档可能超出窗口，导致无法完整输入

**2. 检索精度**
- 整个文档作为检索单元，相关性评分会被稀释
- 例如：100 页文档中只有 1 页相关，整体相似度会很低
- 切分后，相关 chunk 能获得更高的相似度分数

**3. 生成质量**
- 给 LLM 提供精确相关的片段，而非大量噪声
- 减少幻觉，提高答案准确性
- 降低 token 消耗和成本

**4. 存储效率**
- 细粒度索引更容易管理和更新
- 可以针对性地删除或替换某个 chunk

#### 实际案例

假设用户查询："Python 的装饰器怎么用？"

- **不切分**：检索到整本《Python 编程从入门到实践》（500 页），相似度 0.3
- **切分后**：检索到"装饰器章节"（2 页），相似度 0.85

显然，切分后的结果更精准。

---

### Q2：常见的文档切分策略有哪些？各自的优缺点是什么？

#### 1. 固定长度切分（Fixed-size Chunking）

**原理**：按固定字符数或 token 数切分

**优点**：
- 实现简单
- chunk 大小可控

**缺点**：
- 可能在不合适的地方截断（如句子中间）
- 忽略文档结构

**适用场景**：快速原型、对精度要求不高的场景

---

#### 2. 递归字符切分（Recursive Character Splitting）

**原理**：优先在自然分隔符处切分（段落 > 句子 > 词语）

**示例**（LangChain 默认策略）：
```
分隔符优先级：["\n\n", "\n", " ", ""]
chunk_size: 1000, chunk_overlap: 200
```

**优点**：
- 保持语义完整性
- 避免在句子中间截断

**缺点**：
- 可能产生大小不均的 chunk
- 对结构化文档（如 Markdown）效果一般

**适用场景**：通用文本、博客文章、新闻

---

#### 3. 基于结构的切分（Structure-based Chunking）

**原理**：利用文档的层级结构（标题、章节）切分

**示例**（Markdown）：
```markdown
# 一级标题
## 二级标题
### 三级标题
内容...
```
按标题层级切分，每个标题下的内容作为一个 chunk

**优点**：
- 保持文档逻辑结构
- chunk 语义连贯性好

**缺点**：
- 依赖文档格式（需要解析器）
- 某些 chunk 可能过长或过短

**适用场景**：Markdown、HTML、PDF（有明确标题结构）

---

#### 4. 父子文档切分（Parent-Child Chunking）

**原理**：
- **父文档**：大块（如 2000 tokens），用于生成时提供上下文
- **子文档**：小块（如 500 tokens），用于检索提高精度

**流程**：
```
检索阶段：用子文档检索 → 找到最相关的子文档
生成阶段：返回对应的父文档 → LLM 有更完整的上下文
```

**优点**：
- 兼顾检索精度和生成质量
- 解决"小 chunk 信息不足，大 chunk 噪声多"的矛盾

**缺点**：
- 存储成本增加（需要存两份）
- 实现复杂度提高

**适用场景**：对精度要求高的生产环境

---

#### 5. 语义切分（Semantic Chunking）

**原理**：基于 embedding 相似度，在语义变化大的地方切分

**流程**：
1. 将文档按句子切分
2. 计算相邻句子的 embedding 相似度
3. 当相似度低于阈值时，在此处切分

**优点**：
- 保证每个 chunk 内部语义一致
- 自动适应不同长度的段落

**缺点**：
- 需要计算大量 embedding，成本高
- 阈值选择困难

**适用场景**：高质量知识库、专业领域文档

---

### Q3：chunk_size 和 chunk_overlap 如何选择？

#### chunk_size 的选择

**太小（如 100-200 tokens）**：
- ✅ 检索精度高（相关性强）
- ❌ 信息碎片化，缺少上下文
- ❌ 生成时可能需要多个 chunk 拼接

**太大（如 2000+ tokens）**：
- ✅ 上下文完整
- ❌ 检索精度下降（噪声多）
- ❌ token 消耗高

**推荐值**：**500-1000 tokens**（中文场景）

#### chunk_overlap 的作用

**目的**：防止关键信息被切分到两个 chunk 的边界

**示例**：
```
Chunk 1: "...Python 的装饰器是一种特殊的函数，它可以..."
Chunk 2: "...它可以修改其他函数的行为而不改变其源代码..."
```
如果没有 overlap，"装饰器"的定义被割裂了。

**推荐值**：chunk_size 的 **10-20%**
- chunk_size=1000 → overlap=100-200

#### 实际调优方法

1. **基准测试**：准备 50-100 个典型查询
2. **尝试不同配置**：[500/100, 800/150, 1000/200]
3. **评估指标**：召回率、精确率、答案质量
4. **选择最优**：综合性能和成本

## 二、向量与 Embedding

### Q4：嵌入向量的维度选择多少比较好？为什么？

#### 常见维度与推荐

| 维度 | 代表模型 | 适用场景 |
|------|---------|---------|
| 384 | MiniLM-L6、GTE-small | 轻量级场景，资源受限 |
| 768 | BGE-base、GTE-base、E5-base | 通用场景，性能与效果平衡 |
| **1024** | **BGE-large、Qwen3-embedding** | **推荐，中文 RAG 最优区间** |
| 1536 | OpenAI text-embedding-3-large | 高精度场景 |
| 3584 | Qwen3-embedding（原始维度） | 极致精度，存储和计算成本高 |

**推荐维度**：**768 ~ 1024**，中文 RAG 场景下 **1024 维**是最佳平衡点。

#### 维度的本质

**维度 = 向量能编码的语义特征数量**。每一维可以理解为一个"语义轴"，维度越高，模型能区分的语义细节越多。

#### 维度太低（如 128/256）的问题

- 语义表达能力不足，不同含义的文本可能映射到相近的向量（类似哈希碰撞）
- 对于中文这种语义密度高的语言，低维度无法区分"苹果公司"和"苹果水果"
- 检索召回率和精度都会下降

#### 维度太高（如 2048/3584）的问题

- **存储成本线性增长**：1024 维 float32 = 4KB/向量，3584 维 = 14KB/向量。100 万文档的索引从 4GB 增长到 14GB
- **检索延迟增加**：余弦相似度计算复杂度 O(d)，维度翻倍延迟翻倍
- **维度灾难**：高维空间中，所有点之间的距离趋于相等，余弦相似度的区分度反而下降
- **边际收益递减**：从 768→1024 的精度提升明显，但从 1024→2048 的提升很小

#### 1024 维为什么是最优区间

- 足够编码中文的复杂语义（多义词、近义词、上下位关系）
- 存储和计算成本可控（4KB/向量，Milvus HNSW 索引效率高）
- 主流中文 embedding 模型在 1024 维上的 benchmark 表现最优
- 超过 1024 维后，MTEB/C-MTEB 排行榜上的分数提升通常 < 1%，但成本增加 50%+

#### Matryoshka（套娃）降维

现代 embedding 模型支持 **Matryoshka Representation Learning**，训练时让前 N 维也具有良好的语义表达能力：

- 原始维度 3584 → 可截取前 1024 维使用，精度损失 < 2%
- 原始维度 1024 → 可截取前 512 维使用，精度损失约 3-5%

这意味着可以根据实际资源灵活选择维度，而不必重新训练模型。

#### 实际选择建议

| 场景 | 推荐维度 | 理由 |
|------|---------|------|
| 资源充足、追求精度 | 1024 | 中文语义表达最优，主流模型默认输出 |
| 资源受限、百万级文档 | 512~768 | 利用 Matryoshka 降维，存储减半 |
| 超大规模（亿级） | 256~384 | 牺牲精度换取可行性，配合重排序补偿 |
| 多语言混合 | 1024~1536 | 多语言语义空间需要更多维度 |

## 三、多模态 RAG

### Q7：多模态 RAG 中，图片和文字是如何联合检索的？

#### 整体架构

多模态 RAG 的核心思想是：**文字检索和图片检索并行执行，最后在生成阶段融合**。

#### 数据入库阶段

```
PDF 文件
   │
   ├─→ PaddleOCR（文字 OCR）→ 文本 chunks → Milvus 文本 Collection
   │
   ├─→ pypdf（嵌入图片提取）
   │       ├─→ VLM 生成 Caption（可选）
   │       └─→ CLIP Embedding → Milvus 图片 Collection
   │
   └─→ pdfplumber（表格提取）
           ├─→ Markdown 格式 chunk → Milvus 文本 Collection
           └─→ 逐行自然语言摘要 chunk → Milvus 文本 Collection
```

**关键点**：
- 图片入库与文字入库**解耦**，通过异步任务后台执行，不阻塞主流程
- 表格写入两种格式的 chunk（Markdown + 自然语言摘要），提升检索召回率

#### 检索阶段

```
用户查询
   │
   ├─→ 文字检索：Dense (向量) + Sparse (BM25) + RRF 融合 → 重排序
   │
   └─→ 图片检索（并行）：CLIP 文字向量 → 各 collection 并行检索
           ├─→ score 阈值过滤（默认 0.25）
           ├─→ image_id 跨 collection 去重
           └─→ 混合图文 RRF 融合排序
```

**关键技术**：
- **CLIP 模型**：`openai/clip-vit-base-patch32`（512维），支持本地缓存
- **并行检索**：对所有知识库 collection 使用 `asyncio.gather()` 并发检索
- **阈值过滤**：默认 score ≥ 0.25 才保留，避免低相关图片干扰
- **image_id 去重**：跨 collection 按 image_id 去重，保留最高分
- **混合图文 RRF**：图片 CLIP score 归一化后与文字 rerank score 对齐，统一排序

#### 生成阶段

- **最终答案 + 合格图片**：调用多模态 VLM（如 qwen-vl-plus），传入文字 + top-N 图片 base64
- **子问题阶段 / 无合格图片**：退化为纯文字 LLM 生成，避免中间答案被无关图片干扰
- **数量控制**：最多传入 3 张图片，防止超出 VLM token 限制

#### 优势

- **真正的多模态理解**：不是简单的图片 caption 转文字，而是 VLM 直接理解图片内容
- **并行高效**：文字和图片检索同时执行，不增加延迟
- **智能过滤**：通过阈值和数量控制，只传入最相关的图片

### Q8：CLIP 模型如何实现跨模态检索？

#### CLIP 的核心思想

**CLIP（Contrastive Language-Image Pre-training）** 通过在大规模图文对数据集上对比学习，将图片和文字映射到**同一向量空间**。

#### 工作原理

```
训练阶段：
图片 → CLIP Image Encoder → 图片向量
文字 → CLIP Text Encoder → 文字向量
                    ↓
      对比学习：拉近相关图文对的向量距离，推远不相关的
```

**推理阶段**：
- 图片向量化：`embed_image_bytes(image_bytes)` → 512 维向量
- 文字向量化：`embed_text("查询文本")` → 512 维向量
- 余弦相似度：计算图片向量和文字向量的相似度，找到最相关的图片

#### 为什么能跨模态？

- CLIP 在 4 亿图文对上训练，学习了图片和文字的语义对应关系
- 例如："一只猫坐在沙发上"的文字向量，与真实猫坐沙发的图片向量，在向量空间中距离很近
- 这使得可以用文字查询图片，也可以用图片查询相似图片

#### 本项目的应用

- **模型选择**：`openai/clip-vit-base-patch32`（512维），平衡精度和效率
- **本地缓存**：支持指定本地模型路径，生产环境无需访问 HuggingFace
- **异步推理**：CLIP 推理通过 `asyncio.to_thread` 放入线程池，不阻塞事件循环

## 四、对话与记忆

### Q9：如何处理长对话历史，避免超出 LLM 上下文窗口？

#### 问题背景

随着对话轮次增加，`messages` 列表无限增长：
- 可能超出 LLM 上下文窗口（如 8K/32K tokens）
- 即使未超出，也会显著增加 token 消耗和延迟
- 早期对话中的关键信息可能被截断

#### 解决方案：三层压缩策略

**策略 1：跨轮对话历史压缩**

**触发条件**（任一满足即触发）：
- 轮数 > 10 轮（20 条消息）
- Token 数 > 4000

**压缩机制**：
- 使用 LLM 将旧消息压缩为摘要 SystemMessage
- 保留最近 3-4 轮原始消息
- 如果旧消息总量过大，分批压缩再合并

**示例**：
```
压缩前：20 条消息（用户和助手交替）
压缩后：
  - SystemMessage: "[对话历史摘要] 用户询问了 Python 的基础语法...助手解释了变量、函数..."
  - HumanMessage: "那装饰器怎么用？"（最近一轮）
  - AIMessage: "装饰器的用法是..."（最近一轮）
```

**策略 2：对话上下文窗口自适应**

**原理**：根据 token 预算动态调整保留的原文和摘要比例

**机制**：
- 预算内（如 2000 tokens）：保留原文
- 超出部分：使用 LLM 生成摘要补充
- 优先保留包含关键实体和决策的消息

**策略 3：渐进式摘要**

**触发条件**：每隔 5 轮触发一次增量摘要

**机制**：
- 带锚点防护的增量摘要，防止关键信息漂移
- 累积跨轮对话摘要，存储在 State 中
- 新摘要 = 旧摘要 + 新增内容的压缩

#### 技术要点

- **RemoveMessage 机制**：LangGraph 中使用 RemoveMessage 删除旧消息，再追加压缩后的消息
- **分批压缩**：当旧消息总 token 超过安全上限（如 6000）时，分批压缩再合并，避免压缩调用本身超出上下文窗口
- **Token 估算**：中文 1 字符 ≈ 1.5 token，英文 1 单词 ≈ 1 token，混合场景取折中值（字符数 × 0.6）

### Q10：多跳推理中，如何管理和传递推理状态？

#### 多跳推理的挑战

复杂问题需要分解为多个子问题逐一解决，例如：
- "李呈瑞获得过哪些勋章？这些勋章的授予条件是什么？"
  - 子问题 1：李呈瑞获得过哪些勋章？
  - 子问题 2：这些勋章的授予条件是什么？

**挑战**：
- 需要维护子问题队列
- 需要记录已解决的上下文
- 需要处理子问题失败的情况
- 需要防止无限循环

#### State 设计

```python
class State(MessagesState):
    original_query: str  # 原始查询
    sub_questions: List[str]  # 待解决的子问题队列
    current_sub_question: str  # 当前正在处理的子问题
    reasoning_context: str  # 已解决的上下文（子问题 + 答案）
    reasoning_steps: List[dict]  # 推理过程记录（用于前端展示）
    grade_retry_count: int  # 评分重试计数（防止死循环）
```

#### 流程控制

```
START
  │
  ▼
retrieve_or_respond（判断是否需要检索）
  │
  ├─ need_retrieval=false ──→ final ──→ END
  │
  └─ need_retrieval=true ──→ prepare_next_step
                                │
                                ├─ 子问题队列为空 → 分解多跳问题
                                └─ 子问题队列非空 → 取出第一个子问题
                                │
                                ▼
                        enhance_and_route_current（查询增强 + 路由）
                                │
                                ▼
                          fusion_retrieve（融合检索）
                                │
                        ┌───────┴───────┐
                        │               │
                    grade=good      grade=bad（最多重试 2 次）
                        │               │
                        ▼               └──→ enhance_and_route_current
                generate_current_answer（生成当前子问题答案）
                        │
                ┌───────┴───────┐
                │               │
          有子问题          无子问题
                │               │
                ▼               ▼
        prepare_next_step   synthesize（整合所有子问题答案）
              (循环)                      │
                                          ▼
                                        final ──→ END
```

#### 关键机制

**1. 子问题分解**
- 使用 LLM 将复杂问题分解为子问题队列
- 分解失败时回退到单跳（原始问题作为唯一子问题）
- 通过 SSE 向前端推送分解结果，提升透明度

**2. 推理上下文管理**
- 每解决一个子问题，将"问题 + 答案"追加到 reasoning_context
- 当 reasoning_context 过长时，使用 LLM 压缩为摘要
- 压缩阈值：默认 5000 字符

**3. 防死循环**
- grade_retry_count：每个子问题最多重试 2 次，超过后强制通过
- 避免评分一直失败导致无限循环

**4. 引用溯源**
- 记录每个子问题引用的文档编号 [1][2][3]
- 最终答案附加完整的引用链，展示每个子问题的来源

## 五、系统架构与工程化

### Q11：LangGraph 的状态机是如何设计的？有哪些核心节点？

#### LangGraph 简介

LangGraph 是一个用于构建有状态、多参与者应用的状态机框架，特别适合 RAG 这类需要复杂流程控制的场景。

#### State 定义

State 是整个流程的核心数据结构，继承自 `MessagesState`（包含 messages 字段），并扩展了 RAG 特有的字段：

```python
class State(MessagesState):
    original_query: str  # 原始查询
    task_characteristics: TaskCharacteristics  # 任务分析特征
    need_retrieval: bool  # 是否需要增强检索
    router_index: Dict[str, List[str]]  # 查询路由（collection → queries）
    search_content: str  # 检索内容整合（带来源编号）
    retrieved_documents: List[str]  # 检索到的文档列表
    retrieved_images: List  # CLIP 图片检索结果
    retrieval_scores: List[float]  # 重排序分数
    run_count: int  # 运行次数
    grade_retry_count: int  # 评分重试计数
    answer: str  # 最终答案
    sub_questions: List[str]  # 待解决的子问题队列
    current_sub_question: str  # 当前正在处理的子问题
    reasoning_context: str  # 已解决的上下文
    reasoning_steps: List[dict]  # 推理过程记录
    conversation_summary: str  # 渐进式摘要
```

#### 7 个核心节点

| 节点 | 所属 Mixin | 职责 |
|------|-----------|------|
| `retrieve_or_respond` | RouteNodeMixin | 入口节点：任务分析、对话压缩、判断是否需要检索 |
| `prepare_next_step` | RouteNodeMixin | 子问题分解或准备当前子问题 |
| `enhance_and_route_current` | RouteNodeMixin | 查询增强 + 路由到目标知识库 |
| `fusion_retrieve` | RetrievalNodeMixin | 融合检索（内部 + 外部）+ 近似去重 + 重排序 + 多模态图片检索 |
| `grade_documents` | RetrievalNodeMixin | 文档评分：基于 embedding 相似度逐文档评分 |
| `generate_current_answer` | GenerateNodeMixin | 生成当前查询的答案（支持流式、多模态、置信度计算） |
| `synthesize` | GenerateNodeMixin | 多跳场景下合并子问题答案 + 引用溯源 |
| `final` | GenerateNodeMixin | 最终输出：存储问答对、可选触发评估 |

#### 图结构（边定义）

```
START
  │
  ▼
retrieve_or_respond
  │
  ├─ need_retrieval=false ──→ final ──→ END
  │
  └─ need_retrieval=true ──→ prepare_next_step
                                │
                                ▼
                        enhance_and_route_current
                                │
                                ▼
                          fusion_retrieve
                                │
                        ┌───────┴───────┐
                        │               │
                    grade=good      grade=bad
                        │               │
                        ▼               └──→ enhance_and_route_current（重试）
                generate_current_answer
                        │
                ┌───────┴───────┐
                │               │
          有子问题          无子问题
                │               │
                ▼               ▼
        prepare_next_step   synthesize
                                │
                                ▼
                              final ──→ END
```

#### 持久化

- **对话状态**：`AsyncPostgresSaver`（LangGraph Checkpointer）自动持久化 State，支持跨请求恢复
- **长期记忆**：`AsyncPostgresStore` 存储用户偏好、问答对等结构化记忆
- **向量索引**：Milvus 存储文档 embedding

### Q12：如何实现流式输出，让用户实时看到生成进度？

#### 传统方式的局限

使用 `ainvoke()` 同步返回，用户需等待完整生成后才能看到结果，体验差。

#### 流式输出的实现

**核心技术**：LangGraph 的 `astream()` + SSE（Server-Sent Events）

**实现步骤**：

1. **定义流式入口**：`graph.start_stream()` 替代 `graph.start()`

2. **设置 stream_mode**：
   ```python
   async for event_chunk in graph.astream(
       input_data, config, 
       stream_mode=["messages", "updates", "custom"]
   ):
       # 处理不同类型的事件
   ```

3. **处理不同类型的事件**：
   - `messages` 模式：捕获 LLM 生成的 token（AIMessageChunk）
   - `updates` 模式：捕获节点状态更新（如子问题分解）
   - `custom` 模式：自定义事件（如检索进度）

4. **Token 过滤机制**（基于 tags 精确区分）：
   - 核心生成函数的 chain 加上 `tags=["stream_to_user"]`
   - 辅助性调用不加 tag
   - 通过 `metadata["tags"]` 过滤，只展示需要用户看到的 token

5. **前端 SSE 接收**：
   ```javascript
   const eventSource = new EventSource('/api/chat/stream');
   eventSource.onmessage = (event) => {
       const data = JSON.parse(event.data);
       if (data.type === 'token') {
           // 逐字显示
       } else if (data.type === 'decomposition') {
           // 展示子问题分解
       }
   };
   ```

#### 心跳保活

**问题**：长时间无 token 输出时，连接可能超时断开。

**解决方案**：每 15 秒发送一次 heartbeat 事件，保持连接活跃。

#### 前端取消支持

**机制**：检查 `asyncio.current_task().cancelled()`，如果任务被取消则立即中断流式输出，释放资源。

#### 优势

- **首字延迟**：从数秒降至毫秒级
- **用户体验**：实时看到生成进度，减少等待焦虑
- **透明度**：展示子问题分解、检索进度等中间状态

## 六、性能优化与容错

### Q13：如果 Milvus 集群出现故障，检索服务如何降级？

#### 降级策略分级

| 降级级别 | 触发条件 | 策略 | 影响 |
|---------|---------|------|------|
| Level 1 | Milvus 单节点故障 | 自动切换到其他节点 | 无影响 |
| Level 2 | Milvus 集群不可用 | 只走 BM25 检索 | 召回率下降 20-30% |
| Level 3 | 数据库也不可用 | 只走外部 MCP 搜索 | 依赖外部服务 |
| Level 4 | 所有检索失败 | 返回缓存结果或提示用户 | 无法提供新信息 |

#### 熔断器模式

**原理**：当某个服务连续失败多次后，暂时停止调用该服务，直接走降级方案，避免雪崩效应。

**实现要点**：
- 失败阈值：连续失败 5 次触发熔断
- 恢复超时：60 秒后尝试恢复
- 半开状态：恢复后先试一次，成功则完全恢复，失败则继续熔断

#### 缓存兜底

**策略**：缓存热门查询结果，当所有检索都失败时，返回缓存结果。

**实现**：
- 使用 TTLCache，最大容量 1000 条，过期时间 1 小时
- 先查缓存，命中则直接返回
- 未命中则走检索流程，结果存入缓存

#### 实际案例

假设 Milvus 集群因网络分区不可用：

1. 检测到 Milvus 连接超时
2. 触发熔断器，跳过 Milvus 检索
3. 降级到 BM25 检索（本地索引，不依赖外部服务）
4. 如果 BM25 也失败，降级到外部 Bing 搜索
5. 如果所有检索都失败，返回缓存结果或友好提示

### Q14：如何优化检索性能，降低延迟？

#### 查询增强并行化

**问题**：同义改写、扩展改写、专业化改写、HyDE 预测、查询分解共 5 个 LLM 调用，如果串行执行耗时很长。

**解决方案**：使用 `RunnableParallel` 并行执行所有增强策略。

**效果**：
- 同步请求：平均 4s
- 并行化后：平均 1~1.5s
- **性能提升 3-4 倍**

#### 多查询并行检索

**问题**：多个增强后的查询如果串行检索，延迟累加。

**解决方案**：使用 `asyncio.gather()` 并行检索所有查询。

#### 内部/外部检索并行化（待优化）

**当前问题**：先完成内部检索再做外部检索，串行执行。

**改进方向**：将 `_retrieve_internal` 和 `_retrieve_external` 改为 `asyncio.gather()` 并行执行。

#### 图片检索并行化

**实现**：对所有知识库 collection 使用 `asyncio.gather()` 并发发起图片检索。

**效果**：
- 单个 collection 检索耗时 100ms
- 3 个 collection 串行：300ms
- 3 个 collection 并行：~100ms（取决于最慢的那个）

#### CLIP 推理异步化

**问题**：CLIP 图片向量化是 CPU 密集型操作，会阻塞事件循环。

**解决方案**：通过 `asyncio.to_thread` 将 CLIP 推理放入线程池执行。

#### 连接池复用

**实现**：MilvusExecutor 按 collection_name 单例池复用连接，避免每次检索创建新连接。

### Q15：如何处理工具调用（如外部搜索）的超时和重试？

#### 超时控制

**问题**：工具调用（如 Bing 搜索 API）可能因网络问题无限阻塞。

**解决方案**：使用 `asyncio.wait_for(timeout=30)` 添加超时控制。

**示例逻辑**：
```
try:
    result = await asyncio.wait_for(call_tool(), timeout=30)
except asyncio.TimeoutError:
    logger.warning("工具调用超时")
    return fallback_result
```

#### 指数退避重试

**问题**：简单重试（间隔 0 秒）可能在服务短暂不可用时频繁失败。

**解决方案**：指数退避重试，每次重试间隔翻倍。

**重试策略**：
- 第 1 次失败：等待 2^0 = 1 秒后重试
- 第 2 次失败：等待 2^1 = 2 秒后重试
- 第 3 次失败：等待 2^2 = 4 秒后重试
- 超过最大重试次数：返回错误或降级方案

#### 降级策略

**原则**：当某个模块失败时，有明确的降级方案。

**示例**：
- 重排序失败 → 回退到原始排序
- 外部检索失败 → 仅用内部检索结果
- LLM 路由失败 → 回退到全库检索

## 总结

### 核心知识点回顾

1. **检索与排序**：RRF 优于 Weighted Ranker，CrossEncoder Rerank 提升精度 10-20%
2. **向量维度**：1024 维是中文 RAG 的最优平衡点
3. **多模态 RAG**：CLIP 跨模态检索 + VLM 图文联合生成
4. **对话压缩**：跨轮压缩 + 自适应窗口 + 渐进式摘要三层策略
5. **多跳推理**：State 设计、流程控制、防死循环机制
6. **流式输出**：LangGraph astream + SSE + tags 过滤
7. **容错降级**：熔断器、多级降级、缓存兜底
8. **性能优化**：并行化、连接池、异步推理
