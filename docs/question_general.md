## 一、文档切分（Chunking）

### Q1：为什么需要对文档进行切分？直接整个文档检索不行吗？

#### 核心原因

**1. Token 限制**
- LLM 有上下文窗口限制（如 8K/32K tokens）
- 长文档可能超出窗口，导致无法完整输入

**2. 检索精度**
- 整个文档作为检索单元，相关性评分会被稀释
- 例如：100 页文档中只有 1 页相关，整体相似度会很低
- 切分后，相关 chunk 能获得更高的相似度分数

**3. 生成质量**
- 给 LLM 提供精确相关的片段，而非大量噪声
- 减少幻觉，提高答案准确性
- 降低 token 消耗和成本

**4. 存储效率**
- 细粒度索引更容易管理和更新
- 可以针对性地删除或替换某个 chunk

#### 实际案例

假设用户查询："Python 的装饰器怎么用？"

- **不切分**：检索到整本《Python 编程从入门到实践》（500 页），相似度 0.3
- **切分后**：检索到"装饰器章节"（2 页），相似度 0.85

显然，切分后的结果更精准。

---

### Q2：常见的文档切分策略有哪些？各自的优缺点是什么？

#### 1. 固定长度切分（Fixed-size Chunking）

**原理**：按固定字符数或 token 数切分

**优点**：
- 实现简单
- chunk 大小可控

**缺点**：
- 可能在不合适的地方截断（如句子中间）
- 忽略文档结构

**适用场景**：快速原型、对精度要求不高的场景

---

#### 2. 递归字符切分（Recursive Character Splitting）

**原理**：优先在自然分隔符处切分（段落 > 句子 > 词语）

**示例**（LangChain 默认策略）：
```
分隔符优先级：["\n\n", "\n", " ", ""]
chunk_size: 1000, chunk_overlap: 200
```

**优点**：
- 保持语义完整性
- 避免在句子中间截断

**缺点**：
- 可能产生大小不均的 chunk
- 对结构化文档（如 Markdown）效果一般

**适用场景**：通用文本、博客文章、新闻

---

#### 3. 基于结构的切分（Structure-based Chunking）

**原理**：利用文档的层级结构（标题、章节）切分

**示例**（Markdown）：
```markdown
# 一级标题
## 二级标题
### 三级标题
内容...
```
按标题层级切分，每个标题下的内容作为一个 chunk

**优点**：
- 保持文档逻辑结构
- chunk 语义连贯性好

**缺点**：
- 依赖文档格式（需要解析器）
- 某些 chunk 可能过长或过短

**适用场景**：Markdown、HTML、PDF（有明确标题结构）

---

#### 4. 父子文档切分（Parent-Child Chunking）

**原理**：
- **父文档**：大块（如 2000 tokens），用于生成时提供上下文
- **子文档**：小块（如 500 tokens），用于检索提高精度

**流程**：
```
检索阶段：用子文档检索 → 找到最相关的子文档
生成阶段：返回对应的父文档 → LLM 有更完整的上下文
```

**优点**：
- 兼顾检索精度和生成质量
- 解决"小 chunk 信息不足，大 chunk 噪声多"的矛盾

**缺点**：
- 存储成本增加（需要存两份）
- 实现复杂度提高

**适用场景**：对精度要求高的生产环境

---

#### 5. 语义切分（Semantic Chunking）

**原理**：基于 embedding 相似度，在语义变化大的地方切分

**流程**：
1. 将文档按句子切分
2. 计算相邻句子的 embedding 相似度
3. 当相似度低于阈值时，在此处切分

**优点**：
- 保证每个 chunk 内部语义一致
- 自动适应不同长度的段落

**缺点**：
- 需要计算大量 embedding，成本高
- 阈值选择困难

**适用场景**：高质量知识库、专业领域文档

---

### Q3：chunk_size 和 chunk_overlap 如何选择？

#### chunk_size 的选择

**太小（如 100-200 tokens）**：
- ✅ 检索精度高（相关性强）
- ❌ 信息碎片化，缺少上下文
- ❌ 生成时可能需要多个 chunk 拼接

**太大（如 2000+ tokens）**：
- ✅ 上下文完整
- ❌ 检索精度下降（噪声多）
- ❌ token 消耗高

**推荐值**：**500-1000 tokens**（中文场景）

#### chunk_overlap 的作用

**目的**：防止关键信息被切分到两个 chunk 的边界

**示例**：
```
Chunk 1: "...Python 的装饰器是一种特殊的函数，它可以..."
Chunk 2: "...它可以修改其他函数的行为而不改变其源代码..."
```
如果没有 overlap，"装饰器"的定义被割裂了。

**推荐值**：chunk_size 的 **10-20%**
- chunk_size=1000 → overlap=100-200

#### 实际调优方法

1. **基准测试**：准备 50-100 个典型查询
2. **尝试不同配置**：[500/100, 800/150, 1000/200]
3. **评估指标**：召回率、精确率、答案质量
4. **选择最优**：综合性能和成本

## 二、检索策略进阶

### Q4：什么是混合检索？为什么需要混合检索？

#### 单一检索的局限

**纯向量检索（Dense Retrieval）**：
- ✅ 擅长语义匹配（"苹果手机" → "iPhone"）
- ❌ 对专有名词、精确关键词不敏感（"Python 3.12" 可能检索到 "Python 2.7"）

**纯关键词检索（Sparse Retrieval / BM25）**：
- ✅ 擅长精确匹配（"Python 3.12" 精确匹配）
- ❌ 无法理解语义（"手机" 和 "智能手机" 被视为不同词）

#### 混合检索的优势

**核心思想**：结合两者的优势，互补不足

**典型架构**：
```
用户查询
   │
   ├─→ Dense 检索（向量）→ top-k 文档
   │
   └─→ Sparse 检索（BM25）→ top-k 文档
   │
   └─→ RRF 融合 → 最终结果
```

**效果提升**：
- 召回率提升 15-25%
- 对不同类型查询都有良好表现

#### 实际案例

查询："LangGraph 的 State 怎么定义？"

- **向量检索**：找到"LangGraph 状态管理"相关文档（语义匹配）
- **BM25 检索**：找到包含"State"、"定义"关键词的文档（精确匹配）
- **融合后**：两者结合，召回更全面

### Q5：什么是 HyDE（Hypothetical Document Embeddings）？原理是什么？

#### 核心思想

**HyDE**：先让 LLM 生成一个假设性的答案文档，然后用这个假设文档去检索真实文档。

**直觉**：假设答案和真实答案在向量空间中应该很接近。

#### 工作流程

```
用户查询："Python 装饰器的作用是什么？"
    │
    ├─→ LLM 生成假设答案："Python 装饰器是一种设计模式，它允许..."
    │       （可能不完全准确，但语义方向正确）
    │
    └─→ 用假设答案的向量去检索真实文档
            ↓
        找到真正讲解装饰器的文档
```

#### 优势

- **解决查询太短的问题**：短查询的向量表达能力弱，假设文档更丰富
- **语义对齐**：假设答案和真实答案在同一语义空间
- **无需训练**：直接使用现有 LLM 和 embedding 模型

#### 局限

- **幻觉风险**：如果 LLM 生成的假设答案错误，可能误导检索
- **额外延迟**：需要先生成假设答案，再检索
- **成本增加**：每次查询多一次 LLM 调用

#### 改进方案

- **多假设生成**：生成 3-5 个假设答案，取平均向量或投票
- **降低权重**：HyDE 只是检索线索之一，不作为唯一依据
- **后验证**：检索后验证文档是否真的相关

---

### Q6：什么是查询扩展（Query Expansion）？有哪些常见策略？

#### 核心思想

通过扩展原始查询，增加召回的多样性。

#### 常见策略

**1. 同义改写（Paraphrasing）**
- 原始查询："Python 装饰器"
- 扩展查询："Python decorator 用法"、"Python 修饰器教程"

**2. 反向翻译（Back Translation）**
- 中文 → 英文 → 中文
- "机器学习" → "machine learning" → "机器学习"（可能得到不同的表述）

**3. 子问题分解（Query Decomposition）**
- 原始查询："比较 Python 和 Java 的性能差异"
- 分解为：
  - "Python 的性能特点"
  - "Java 的性能特点"
  - "Python vs Java 性能对比"

**4. Step-back Prompting**
- 从具体问题抽象到更通用的概念
- 原始查询："LangGraph 的 State 怎么持久化？"
- Step-back："状态机如何保存和恢复状态？"

#### 注意事项

- **去重**：扩展后的查询可能语义重复，需要去重
- **数量控制**：通常扩展 3-5 个查询即可，过多会增加检索成本
- **并行执行**：多个扩展查询应并行检索，避免延迟累加

## 三、重排序（Reranking）

### Q7：为什么需要 Rerank？直接用向量检索的结果不行吗？

#### 向量检索的局限

**召回阶段的特点**：
- 需要从百万级文档中快速筛选 top-k
- 使用近似最近邻搜索（ANN），牺牲精度换取速度
- 余弦相似度只能衡量向量空间距离，无法捕捉细粒度语义交互

**实际问题**：
- 召回的 top-20 中可能有 5-8 个是噪声（语义相关但不精确匹配）
- 例如：查询"Python 装饰器"，可能召回"Java 注解"（都是元编程概念，语义相近但不对）

#### Rerank 的价值

**精排阶段的作用**：
- 对 top-k 候选文档进行精细排序
- CrossEncoder 能让 query 和 doc 的每个 token 互相交互
- 将真正相关的文档排到前面，噪声文档排到后面或过滤掉

**效果提升**：
- 实验表明，Rerank 可以将 RAG 的答案准确率提升 **10-20%**
- 对于复杂查询（如多跳问题），提升更明显

#### 实际案例

查询："LangGraph 的 State 如何持久化？"

**向量检索 top-5**：
1. LangChain 的状态管理（0.82）← 噪声
2. LangGraph 简介（0.79）← 相关但不精确
3. LangGraph Checkpointer 机制（0.76）← 最相关
4. 状态机设计模式（0.73）← 噪声
5. LangGraph 快速入门（0.71）← 相关但不精确

**CrossEncoder Rerank 后**：
1. LangGraph Checkpointer 机制（0.92）← 提升到第 1
2. LangGraph 简介（0.75）
3. LangGraph 快速入门（0.68）
4. （LangChain 的状态管理被过滤，score=0.3）
5. （状态机设计模式被过滤，score=0.25）

### Q8：CrossEncoder 和 Bi-Encoder 有什么区别？各自适用什么场景？

#### 架构对比

| 维度 | Bi-Encoder（双塔） | CrossEncoder（交叉编码器） |
|------|-------------------|--------------------------|
| 架构 | Query 和 Document **分别**编码为向量，再算余弦相似度 | Query 和 Document **拼接**后一起输入 Transformer，直接输出相关性分数 |
| 速度 | 快（文档向量可预计算，检索时只算 query 向量 + ANN） | 慢（每对 query-doc 都要过一次完整的 Transformer） |
| 精度 | 较低（两段文本独立编码，无法捕捉细粒度交互） | **高**（query 和 doc 的每个 token 都能互相 attend） |
| 用途 | **召回阶段**（从百万文档中快速筛选 top-k） | **精排阶段**（对 top-k 结果重新排序） |

#### 工作原理对比

**Bi-Encoder**：
```
Query → Encoder → Query Vector
Document → Encoder → Document Vector
                    ↓
          余弦相似度（快速，但粗略）
```

**CrossEncoder**：
```
[CLS] Query [SEP] Document [SEP] → Transformer → 相关性分数
                                    ↓
                    Query 和 Document 的所有 token 互相交互（慢，但精准）
```

#### 实际应用

**两阶段检索架构**：
```
第一阶段（召回）：Bi-Encoder
  - 从 100 万文档中检索 top-50
  - 耗时：~50ms
  
第二阶段（精排）：CrossEncoder
  - 对 top-50 逐对打分
  - 返回 top-10
  - 耗时：~500ms
  
总延迟：~550ms（可接受）
```

**为什么不全程用 CrossEncoder？**
- 100 万文档 × CrossEncoder = 数小时，不可接受
- Bi-Encoder 快速缩小范围，CrossEncoder 精细排序，是最佳平衡

### Q9：Rerank 的阈值如何选择？太高或太低有什么问题？

#### 阈值的作用

过滤掉相关性低的文档，避免噪声干扰生成。

#### 阈值过高（如 0.9）

**问题**：
- 可能过滤掉所有文档（尤其是对冷门查询）
- 召回率大幅下降

**示例**：
- 查询："量子纠缠的最新研究进展"
- 如果阈值 0.9，可能没有文档达到，返回空结果

**解决方案**：
- 设置兜底机制：如果全部过滤，保留 top-1
- 动态阈值：根据召回文档的质量自适应调整

#### 阈值过低（如 0.3）

**问题**：
- 保留太多噪声文档
- 生成质量下降，token 浪费

**示例**：
- 查询："Python 装饰器"
- 阈值 0.3 可能保留"Java 注解"、"C++ 宏"等无关文档

**解决方案**：
- 提高阈值到 0.5-0.7
- 增加重排序模型的 fine-tuning

#### 推荐实践

**默认阈值**：0.5-0.7（根据业务场景调整）

**调优方法**：
1. 准备评估数据集（100+ 查询）
2. 测试不同阈值：[0.3, 0.5, 0.7, 0.9]
3. 评估指标：召回率、精确率、答案质量
4. 选择平衡点

**动态阈值策略**：
- 如果召回文档平均分 > 0.8，阈值设为 0.7
- 如果召回文档平均分 < 0.5，阈值设为 0.3
- 避免"一刀切"

## 四、提示工程与生成

### Q10：如何设计 RAG 的 Prompt，减少幻觉？

#### 常见问题

**幻觉来源**：
- LLM 过度依赖训练数据，忽略检索到的文档
- 检索到的文档之间有冲突，LLM 不知道信哪个
- 检索到的文档都不相关，LLM 强行回答

#### Prompt 设计原则

**1. 明确指令**
```
请根据以下检索到的文档回答问题。
如果文档中没有相关信息，请明确说明"根据现有资料，无法回答该问题"。
不要编造信息，不要使用文档之外的知识。
```

**2. 引用来源**
```
回答时，请在句末标注来源，如 [1]、[2]。
如果多个文档支持同一观点，标注所有来源，如 [1][3]。
```

**3. 处理冲突**
```
如果不同文档之间有冲突，请：
1. 指出冲突的存在
2. 说明各文档的观点
3. 如果可能，解释冲突的原因（如时间差异、场景不同）
```

**4. 置信度标注**
```
在回答末尾，请标注置信度：
- 高置信度：多个文档一致支持
- 中置信度：单个文档支持，或文档间有部分冲突
- 低置信度：文档信息不足或有严重冲突
```

#### 实际 Prompt 模板

```
你是一个专业的问答助手。请根据以下检索到的文档回答问题。

【检索到的文档】
[1] {doc1}
[2] {doc2}
[3] {doc3}

【用户问题】
{query}

【回答要求】
1. 严格基于上述文档回答，不要编造信息
2. 如果文档中没有相关信息，请说"根据现有资料，无法回答该问题"
3. 在句末标注来源，如 [1]、[2]
4. 如果文档之间有冲突，请指出并说明各方观点
5. 回答末尾标注置信度（高/中/低）

【你的回答】
```

### Q11：如何处理检索到的文档之间的冲突？

#### 冲突类型

**1. 事实冲突**
- 文档 A："Python 3.12 发布于 2023 年 10 月"
- 文档 B："Python 3.12 发布于 2023 年 11 月"

**2. 观点冲突**
- 文档 A："微服务架构适合大型项目"
- 文档 B："微服务架构增加了系统复杂性，小项目应避免使用"

**3. 时间冲突**
- 文档 A（2020 年）："TensorFlow 是最流行的深度学习框架"
- 文档 B（2024 年）："PyTorch 已超越 TensorFlow 成为主流"

#### 处理策略

**1. 时间优先**
- 保留最新的文档，标记旧文档为"过时信息"
- 适用于技术文档、新闻等时效性强的内容

**2. 来源可信度**
- 官方文档 > 技术博客 > 论坛帖子
- 学术论文 > 媒体报道

**3. 多数投票**
- 如果 3 个文档支持 A，1 个文档支持 B，倾向于 A
- 但要说明少数观点的存在

**4. 透明展示**
- 不强行统一，而是如实展示冲突
- 让用户自行判断

#### 实际案例

查询："Python 3.12 什么时候发布的？"

**检索结果**：
- [1] 官方文档："2023-10-02"
- [2] 技术博客："2023-10-02"
- [3] 新闻网站："2023-11-01"（错误）

**处理方式**：
```
根据官方文档 [1] 和多个技术博客 [2]，Python 3.12 于 2023 年 10 月 2 日发布。

注意：有少数来源 [3] 提到 11 月，这可能是混淆了正式发布和稳定版发布的时间。

置信度：高（多个权威来源一致）
```

## 五、评估指标

### Q12：如何评估 RAG 系统的好坏？有哪些关键指标？

#### 评估维度

**1. 检索质量**

| 指标 | 说明 | 计算方法 |
|------|------|---------|
| **Recall@K** | top-K 中有多少相关文档被召回 | 召回的相关文档数 / 总相关文档数 |
| **Precision@K** | top-K 中有多少是相关文档 | 召回的相关文档数 / K |
| **MRR（Mean Reciprocal Rank）** | 第一个相关文档的排名倒数的平均值 | 越高越好，理想值 1.0 |
| **NDCG（Normalized Discounted Cumulative Gain）** | 考虑排名位置的增益 | 越接近 1.0 越好 |

**2. 生成质量**

| 指标 | 说明 | 评估方式 |
|------|------|---------|
| **忠实度（Faithfulness）** | 答案是否忠实于检索到的文档 | LLM 评判或人工标注 |
| **答案相关性（Answer Relevance）** | 答案是否回答了用户问题 | LLM 评判或人工标注 |
| **上下文利用率（Context Utilization）** | 是否充分利用了检索到的上下文 | 分析答案中的引用 |

**3. 端到端质量**

| 指标 | 说明 | 评估方式 |
|------|------|---------|
| **人工评分** | 真人对答案质量打分（1-5 分） | 最可靠，但成本高 |
| **LLM-as-Judge** | 用更强的 LLM 评判答案质量 | 成本低，可自动化 |
| **用户反馈** | 点赞/点踩、停留时间、二次提问率 | 真实场景数据 |

#### 常用评估框架

**RAGAS（RAG Assessment）**：
- 开源评估框架
- 自动化评估忠实度、答案相关性、上下文召回率等
- 基于 LLM 评判，无需人工标注

**TruLens**：
- 商业评估平台
- 提供详细的追踪和评估报告
- 支持 A/B 测试

#### 实际评估流程

```
1. 准备测试集
   - 100-500 个典型查询
   - 每个查询标注标准答案和相关文档

2. 运行 RAG 系统
   - 记录检索结果和生成的答案

3. 计算指标
   - 检索指标：Recall@5, MRR, NDCG
   - 生成指标：忠实度、答案相关性
   - 端到端指标：人工评分或 LLM-as-Judge

4. 分析结果
   - 找出失败的案例
   - 分析失败原因（检索失败？生成失败？）
   - 针对性优化
```

### Q13：什么是 RAGAS？它评估哪些指标？

#### RAGAS 简介

**RAGAS（RAG Assessment）** 是一个开源的 RAG 系统评估框架，由 explodinggradients 开发。

**核心特点**：
- 基于 LLM 自动评估，无需人工标注
- 提供多个维度的指标
- 易于集成到 CI/CD 流程

#### 主要指标

**1. 忠实度（Faithfulness）**
- **定义**：答案中的陈述是否都能从检索到的上下文中推导出来
- **评分**：0-1，越高越好
- **意义**：衡量幻觉程度

**2. 答案相关性（Answer Relevance）**
- **定义**：答案是否直接回答了用户的问题
- **评分**：0-1，越高越好
- **意义**：衡量答案的针对性

**3. 上下文召回率（Context Recall）**
- **定义**：检索到的上下文中包含了多少标准答案所需的信息
- **评分**：0-1，越高越好
- **意义**：衡量检索质量

**4. 上下文精确率（Context Precision）**
- **定义**：检索到的上下文中有多少是相关的
- **评分**：0-1，越高越好
- **意义**：衡量检索的噪声水平

**5. 上下文实体召回率（Context Entity Recall）**
- **定义**：检索到的上下文中包含了多少标准答案中的关键实体
- **评分**：0-1，越高越好
- **意义**：衡量检索是否抓住了关键点

#### 使用示例

```python
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_recall

# 准备数据
data_samples = {
    'question': ['Python 装饰器的作用是什么？'],
    'answer': ['Python 装饰器允许修改函数的行为...'],
    'contexts': [['文档1内容', '文档2内容']],
    'ground_truth': ['标准答案']
}

# 评估
results = evaluate(
    data_samples,
    metrics=[faithfulness, answer_relevancy, context_recall]
)

print(results)
# faithfulness: 0.85
# answer_relevancy: 0.92
# context_recall: 0.78
```

## 六、场景化问题

### Q14：如果 RAG 系统回答不准确，如何排查问题？

#### 排查思路

**第一步：定位问题阶段**

```
用户查询 → 检索 → 生成 → 答案
              ↑         ↑
         检索有问题？  生成有问题？
```

**第二步：检查检索质量**

**问题 1：召回的文档不相关**
- **原因**：
  - embedding 模型效果差
  - 切分策略不合理
  - 查询增强不足
- **解决方案**：
  - 更换更好的 embedding 模型
  - 调整 chunk_size 和切分策略
  - 引入查询扩展（HyDE、同义改写）

**问题 2：相关文档被过滤掉**
- **原因**：
  - 重排序阈值过高
  - 近似去重误删
- **解决方案**：
  - 降低重排序阈值
  - 调整去重阈值或关闭去重测试

**第三步：检查生成质量**

**问题 1：LLM 忽略检索到的文档**
- **原因**：
  - Prompt 不够明确
  - 检索到的文档太多，LLM 无法聚焦
- **解决方案**：
  - 优化 Prompt，强调"严格基于文档"
  - 减少传入的文档数量（top-5 而非 top-20）

**问题 2：LLM 编造信息**
- **原因**：
  - 检索到的文档都不相关
  - LLM 过度依赖训练数据
- **解决方案**：
  - 在 Prompt 中明确要求"如果文档中没有相关信息，请说明无法回答"
  - 添加置信度标注

#### 调试工具

**1. 可视化检索结果**
- 展示 top-10 召回文档及其相似度分数
- 标注哪些是相关的，哪些是噪声

**2. 日志记录**
- 记录每个阶段的输入输出
- 便于回溯分析问题

**3. A/B 测试**
- 对比不同配置的效果
- 如：有无 Rerank、不同 chunk_size

### Q15：RAG 系统在生产环境中需要注意哪些问题？

#### 1. 性能优化

**延迟控制**：
- 目标：P95 延迟 < 2 秒
- 策略：
  - 查询增强并行化
  - 多查询并行检索
  - 缓存热门查询结果
  - 流式输出降低首字延迟

**成本控制**：
- LLM 调用成本高
- 策略：
  - 缓存重复查询的答案
  - 对小问题直接回复，不检索
  - 使用更小的 LLM 处理简单任务

#### 2. 稳定性保障

**容错降级**：
- Milvus 故障 → 降级到 BM25
- LLM 超时 → 返回友好提示
- 外部搜索失败 → 仅用内部检索

**监控告警**：
- 监控关键指标：延迟、错误率、召回率
- 设置告警阈值：P95 延迟 > 3 秒、错误率 > 5%

#### 3. 数据安全

**权限控制**：
- 不同用户只能访问授权的知识库
- 敏感文档加密存储

**审计日志**：
- 记录所有查询和答案
- 便于追溯和合规审查

#### 4. 持续优化

**反馈闭环**：
- 收集用户反馈（点赞/点踩）
- 定期分析失败案例
- 迭代优化检索和生成策略

**A/B 测试**：
- 新配置先在小流量测试
- 验证效果后再全量上线

### Q16：RAG 系统适合什么场景？不适合什么场景？

#### 适合的场景

**1. 知识密集型问答**
- 企业知识库问答
- 技术文档查询
- 法律法规咨询

**特点**：
- 有大量结构化/半结构化文档
- 答案需要准确引用来源
- 知识更新频繁，需要实时检索

**2. 长尾问题**
- 用户问题多样，无法预先准备所有答案
- 传统 FAQ 无法覆盖

**3. 多源信息整合**
- 需要从多个文档中提取信息并综合
- 如：对比不同产品的特性

#### 不适合的场景

**1. 简单事实查询**
- "今天天气怎么样？"
- "1+1等于几？"
- **原因**：直接调用 API 或硬编码更高效

**2. 创意生成**
- "写一首诗"
- "设计一个 Logo"
- **原因**：不需要检索外部知识，纯 LLM 生成更好

**3. 实时性极强的场景**
- "现在股票价格是多少？"
- **原因**：RAG 的检索延迟可能无法满足实时要求

**4. 需要深度推理的场景**
- "证明哥德巴赫猜想"
- **原因**：RAG 主要提供事实检索，不具备复杂推理能力

#### 决策建议

**使用 RAG 的判断标准**：
1. 是否有大量外部知识需要检索？
2. 答案是否需要引用来源？
3. 知识是否频繁更新？
4. 用户对准确性的要求高于创造性？

如果以上问题的答案是"是"，则适合使用 RAG。

### 核心知识点回顾

1. **文档切分**：选择合适的切分策略和参数，平衡检索精度和上下文完整性

3. **重排序**：CrossEncoder 精排提升答案准确率 10-20%
4. **提示工程**：明确指令、引用来源、处理冲突，减少幻觉
5. **评估指标**：Recall、Precision、忠实度、答案相关性等多维度评估
6. **生产实践**：性能优化、容错降级、数据安全、持续优化
